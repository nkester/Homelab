# Feature Action Plan: Plane 1 State & Hardware Consolidation Refactor (Feature 3.4-R)

## Purpose
Recover from lost Talos Linux machine secrets (`talosconfig` / PKI root of trust), transition OpenTofu state management to GitLab's built-in HTTP state backend, consolidate harvested RAM and SATA storage from two donor systems (`HP Pavilion 570-a1xx` and `Dell Inspiron 15R-5537`) into our three active desktop nodes (`HP Compaq Pro 6300 SFF`, `HP Pavilion 590-p0xxx`, and `Lenovo ideacenter 310S-08IAP`), re-align node roles (`controlplane-1`, `worker-1`, `worker-2`) to match hardware capabilities, and declaratively restore all cluster applications via OpenTofu and ArgoCD so the environment is ready to resume Feature 3.5.

## Definition of Done (DoD)
* **DoD 1:** All cluster nodes are re-established through declarative OpenTofu statements backed by GitLab-managed Terraform state, with Talos API access verified across all nodes.
* **DoD 2:** All applications previously deployed up to this point are re-deployed and healthy through ArgoCD and GitOps principles on the new cluster, and the cluster is prepared to begin Feature 3.5.
* **DoD 3:** All documentation (`hardware_inventory.csv`, network IPAM tables, architecture blueprints, bootstrap SOPs, ADRs, engineering logs, and Roadmap) is updated to reflect the new static IP addresses, consolidated hardware specifications, and role changes.

## Phased Execution Plan

### Phase 1: Hardware Audit, Component Consolidation, Role Selection & Baseline Documentation (COMPLETE)
*Audit all candidate computers, consolidate RAM and storage drives into the three active desktop nodes, assign cluster roles, and update architecture and inventory documentation prior to network/cluster provisioning.*

* **Step 1.1: Audit Hardware, Consolidate RAM/Storage & Configure BIOS/UEFI**
  * Audited all 5 systems and harvested components from the two donor systems (`HP Pavilion 570-a1xx` and `Dell Inspiron 15R-5537`):
    * Installed `4GB DDR4 UDIMM` and `1TB 3.5" WDC WD10EZEX-60W HDD` from the `HP 570-a1xx` into the `HP Pavilion 590-p0xxx` (`12GB DDR4` total, `~2TB` across two 3.5" SATA HDDs).
    * Installed one `8GB Samsung PC3L-12800S DDR3L SODIMM` from the `Dell Inspiron 15R` into the `Lenovo ideacenter 310S-08IAP` (`8GB DDR3L` total, retaining its 7200 RPM `465.8GB ST500DM002` HDD).
    * Installed the `931.5GB 2.5" ST1000LM024 HDD` from the `Dell Inspiron 15R` into the `HP Compaq Pro 6300 SFF` lower optical bay using the optical drive SATA data and power connectors (`20GB DDR3` across `2x 8GiB + 2x 2GiB` DIMMs, `256GB SSD` + `931.5GB 2.5" HDD`).
  * Configured BIOS/UEFI settings (`Intel VT-x`, UEFI boot with Secure Boot/CSM disabled, AC Power Recovery).
* **Step 1.2: Assign Node Roles & Retire Donor Chassis**
  * **`controlplane-1` (`10.10.10.51` / VIP `10.10.10.10`):** Assigned to **`HP Compaq Pro 6300 SFF`** (`i7-3770` 4C/8T, 20GB DDR3, 256GB SATA SSD + 931.5GB 2.5" HDD, Intel `e1000e` `eno1`). Retains `etcd` and `kube-apiserver` on the 256GB SSD for low `wal_fsync` latency while adding a 931.5GB secondary disk and 20GB RAM.
  * **`worker-1` (`10.10.10.52`):** Assigned to **`HP Pavilion Desktop 590-p0xxx`** (`i5-8400` 6C/6T, 12GB DDR4, Dual 931.5GB SATA HDDs, Realtek GbE `enp2s0`). Replaces the Lenovo at `.52` as the primary 6-core compute and 2TB storage worker.
  * **`worker-2` (`10.10.10.53`):** Assigned to **`Lenovo ideacenter 310S-08IAP`** (`Celeron J3355` 2C/2T, upgraded to 8GB DDR3L RAM, 465.8GB 7200 RPM HDD, Realtek GbE `enp2s0`). Re-assigned from `.52` to `.53` to replace the retired Dell laptop, with 2x its previous memory (`8GB` vs `4GB`).
  * **Retired Hardware:** Permanently retired the stripped **`HP Pavilion Desktop 570-a1xx`** and **`Dell Inspiron 15R-5537` laptop**.
* **Step 1.3: Update Inventory, Architecture Blueprints, Roadmap & Engineering Log (DoD 3 Baseline)**
  * Updated `docs/hardware_inventory.csv`, `docs/HomeLab_Project_Roadmap.csv`, `README.md`, `infrastructure/networking/README.md`, `infrastructure/storage/README.md`, `docs/architecture/README.md`, `docs/architecture/01-physical-network.md`, `docs/architecture/02-talos-os.md`, `docs/architecture/05-distributed-storage.md`, `docs/architecture/07-object-storage-foundation.md`, and created `docs/logs/epic-3-refactor-hardware-and-state-consolidation.md`.

### Phase 2: Network DHCP Reservations, GitLab OpenTofu State Backend & Modular IaC Setup
*Configure the router DHCP reservations for the new MAC-to-IP bindings, initialize GitLab's remote Terraform HTTP state backend, and refactor the OpenTofu configurations to support one-node-at-a-time provisioning.*

* **Step 2.1: Configure Router DHCP/IPAM Address Reservations (`ER605`)**
  * In the `TP-Link Omada ER605` router UI (`192.168.1.1`), update the VLAN 10 (`10.10.10.0/24`) DHCP Address Reservation table to bind each node's wired MAC address to its static IP so nodes booting into Talos Maintenance Mode at the primary workstation receive their designated IP:
    * `controlplane-1` (`HP Compaq Pro 6300 SFF`) → `10.10.10.51` (`A0-48-1C-98-4E-E3` — unchanged)
    * `worker-1` (`HP Pavilion 590-p0xxx`) → `10.10.10.52` (`28-3A-4D-07-EE-65` — replaces Lenovo on `.52`)
    * `worker-2` (`Lenovo ideacenter 310S`) → `10.10.10.53` (`6C-4B-90-45-42-16` — moved from `.52` to `.53`, replacing retired Dell laptop)
  * Verify that Control Plane VIP (`10.10.10.10`) and Cilium LoadBalancer IPAM pool (`10.10.10.17`–`10.10.10.25`) remain outside the dynamic DHCP allocation range.
* **Step 2.2: Configure & Initialize GitLab HTTP State Backend (Zero-Token-in-Git)**
  * In GitLab (`https://gitlab.com/nkester-personal-cloud/homelab`), create a Project Access Token with `api` scope for OpenTofu state management.
  * Export `GITLAB_USER`, `GITLAB_TOKEN`, and `GITLAB_PROJECT_ID` in the local shell environment (strictly excluded from Git via `.gitignore`).
  * Add `backend "http" {}` to `infrastructure/bootstrap/main.tf`, create `infrastructure/bootstrap/init-state.sh` (with `set -euo pipefail`) and `infrastructure/bootstrap/.env.example`, and run `./init-state.sh` to bind the workspace to GitLab (`homelab-bootstrap` state).
* **Step 2.3: Verify Sidero Image Factory Schematics & Bootable USB**
  * Because `controlplane-1` uses Intel `e1000e` (schematic `613e1592b2da41ae5e265e8789429f22e121aab91cb4deb6bc3c0b6262961245:v1.13.7`) and both `worker-1` (`HP 590`) and `worker-2` (`Lenovo 310S`) use Realtek `r8169` (`RTL8111/8168`, schematic `71405e3fe611adf767ae6e03aa4bf7535f53b8f7abbdc24a466b65d06af43a09:v1.13.7`), verify the existing Talos `v1.13.7` USB installer stick is ready.
* **Step 2.4: Refactor OpenTofu for Iterative One-Node-at-a-Time Provisioning**
  * Refactor `infrastructure/bootstrap/main.tf` (with `variables.tf` / `terraform.tfvars`) so that:
    * `talos_machine_secrets.this` is generated once on the first `tofu apply` and stored permanently in GitLab's encrypted HTTP state.
    * `controlplane-1` (`10.10.10.51/24`, VIP `10.10.10.10`) installs Talos to `/dev/sda` (256GB SSD), mounts `/dev/sdb` (931.5GB HDD) for Longhorn, and sets `allowSchedulingOnControlPlanes = true`.
    * Worker nodes are driven dynamically by a `for_each = var.worker_nodes` map (allowing `worker_nodes` to start empty `{}` during Control Plane provisioning and expand one node at a time as each worker is staged at the workstation).
    * `helm_release.cilium` is configured with `kubeProxyReplacement = true`, `k8sServiceHost = "10.10.10.10"`, `l2announcements.enabled = true`, and `k8sClientRateLimit` (`qps = 50`, `burst = 100`).

### Phase 3: Iterative Bare-Metal Node Provisioning (Workstation Staging → Enclave Placement — DoD 1)
*Stage one machine at a time at the primary workstation, boot into Talos Maintenance Mode, apply its OpenTofu configuration (persisting state to GitLab), relocate the machine to its final resting place on the `TL-SG108E` switch, and verify health before moving to the next machine.*

* **Step 3.1: Stage, Provision & Relocate Control Plane Node (`controlplane-1` — `HP Compaq Pro 6300 SFF` at `10.10.10.51`)**
  1. Connect `HP Compaq Pro 6300 SFF` at the primary workstation, boot from the Talos `v1.13.7` USB into **Maintenance Mode**, and verify it responds to ping at `10.10.10.51`.
  2. Enumerate its logical Ethernet interface (`eno1`) and storage devices (`256GB SSD` and `931.5GB 2.5" HDD`) via `talosctl get links --nodes 10.10.10.51 --insecure` and `talosctl get disks --nodes 10.10.10.51 --insecure`.
  3. With `worker_nodes = {}` in `terraform.tfvars`, execute `tofu apply` to push the Control Plane configuration, install Talos to the 256GB SSD, bootstrap `etcd`, establish Layer 2 VIP `10.10.10.10`, deploy Cilium CNI, and save State Version 1 (`talos_machine_secrets`) to GitLab.
  4. Extract `talosconfig` (`tofu output -raw talosconfig > ~/.talos/config && chmod 600 ~/.talos/config`) and `kubeconfig` (`talosctl --nodes 10.10.10.51 kubeconfig ~/.kube/config && chmod 600 ~/.kube/config`).
  5. Shut down `controlplane-1` (`talosctl shutdown --nodes 10.10.10.51`), move it to its final resting place on **`TL-SG108E` Port 1**, power it on, and verify `10.10.10.51` and VIP `10.10.10.10` report `Ready` before staging `worker-1`.
* **Step 3.2: Stage, Provision & Relocate Worker Node 1 (`worker-1` — `HP Pavilion 590-p0xxx` at `10.10.10.52`)**
  1. Connect `HP Pavilion 590-p0xxx` at the primary workstation, boot from the Talos `v1.13.7` USB into **Maintenance Mode**, and verify it responds to ping at `10.10.10.52`.
  2. Enumerate its logical Ethernet interface (`enp2s0`) and dual 1TB SATA HDDs (`ST1000DM003` and `WD10EZEX`) via `talosctl get links --nodes 10.10.10.52 --insecure` and `talosctl get disks --nodes 10.10.10.52 --insecure`.
  3. Add `worker-1` to the `worker_nodes` map in `terraform.tfvars` and execute `tofu apply` (OpenTofu reads `talos_machine_secrets` from GitLab State, provisions `worker-1`, and saves State Version 2 to GitLab).
  4. Shut down `worker-1` (`talosctl shutdown --nodes 10.10.10.52`), move it to its final resting place on **`TL-SG108E` Port 2**, power it on, and verify it joins the cluster and reports `Ready` before staging `worker-2`.
* **Step 3.3: Stage, Provision & Relocate Worker Node 2 (`worker-2` — `Lenovo ideacenter 310S` at `10.10.10.53`)**
  1. Connect `Lenovo ideacenter 310S` at the primary workstation, boot from the Talos `v1.13.7` USB into **Maintenance Mode**, and verify it responds to ping at `10.10.10.53`.
  2. Enumerate its logical Ethernet interface (`enp2s0`) and 465.8GB HDD (`ST500DM002`) via `talosctl get links --nodes 10.10.10.53 --insecure` and `talosctl get disks --nodes 10.10.10.53 --insecure`.
  3. Add `worker-2` to the `worker_nodes` map in `terraform.tfvars` and execute `tofu apply` (saves State Version 3 to GitLab).
  4. Shut down `worker-2` (`talosctl shutdown --nodes 10.10.10.53`), move it to its final resting place on **`TL-SG108E` Port 3**, power it on, and verify all 3 nodes report `Ready` in their final enclave positions.

### Phase 4: Declarative GitOps Bootstrap & Application Restoration (DoD 2)
*Bootstrap ArgoCD declaratively via OpenTofu and reconcile the App-of-Apps tree (`argocd/root-app.yaml`) to restore all platform services and workloads.*

* **Step 4.1: Provision Out-of-Band Bootstrap Secrets & Declarative ArgoCD Release**
  * Enable the declarative ArgoCD bootstrap resources in OpenTofu (`helm_release` / `kubernetes_manifest` for namespace `argocd`, ArgoCD core installation, `argocd-cm` patch, and `argocd/root-app.yaml`) along with unversioned sensitive bootstrap secrets for External Secrets Operator (`gitlab-eso-token` in `external-secrets`) and GitLab Runner (`gitlab-runner-secret` in `gitlab-runner`), and execute `tofu apply`.
* **Step 4.2: Verify Cascading ArgoCD Sync Waves (`argocd/root-app.yaml`)**
  * Confirm ArgoCD automatically reconciles all previously deployed applications across Sync Waves `-1` through `2` without imperative `kubectl` mutations:
    * **Sync Wave `-1`:** `system-config` (`argocd-cm` `CiliumIdentity` resource exclusion).
    * **Sync Wave `0`:** `cilium-lb-ipam` (`10.10.10.17`–`10.10.10.25` pool & L2 policy), `external-secrets-operator`, `argo-workflows`, `gitlab-runner`.
    * **Sync Wave `1`:** `external-secrets-config` (`ClusterSecretStore`), `longhorn` (distributed block storage across the upgraded multi-disk nodes & default `longhorn` StorageClass), `ingress-nginx` (LoadBalancer IP `10.10.10.17`), `minio-operator`, `knative-operator`.
    * **Sync Wave `2`:** `minio-tenant` (S3 API & `velero-backups` bucket provisioning job), `knative-serving` (Knative Serving control plane & Kourier gateway on LoadBalancer IP `10.10.10.18`), `knative-test-service` (`helloworld-go`).
